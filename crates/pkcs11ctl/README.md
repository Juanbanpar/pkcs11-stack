# pkcs11ctl

PKCS#11 inspection, cryptography and token administration through `pkcs11-client`.

## Build and invocation

```sh
cargo build --release -p pkcs11ctl --locked
./target/release/pkcs11ctl --help
```

```sh
pkcs11ctl --module /absolute/path/to/trusted-pkcs11.so tokens
pkcs11ctl --module /absolute/path/to/trusted-pkcs11.so --format json info
pkcs11ctl sign --help
```

`--module` selects trusted executable vendor code; a URI never loads a library.
`--module` and `--format text|json` may appear before or after a command.
Help/version and verification with `--certificate-file` need no module.

Prefer stable token serials and binary object IDs. Full token criteria are checked;
object operations need stable token/object constraints and exactly one match.
Unknown constraints, PIN queries and persistent slot IDs fail before module loading.
Listed URIs are selectors, not uniqueness guarantees; duplicate IDs/labels remain
ambiguous and empty fields remain exact empty criteria. Private-key selectors need
`type=private`, certificates `type=cert`. Slot IDs serve discovery and initialization.

## Commands

Use `pkcs11ctl COMMAND --help` for complete options.

| Commands | Purpose |
| --- | --- |
| `info`, `slots`, `tokens` | Library, slot and token metadata, including stable token URIs |
| `mechanisms`, `function-support` | Advertised mechanisms, typed executable paths and interface functions |
| `generation-options` | Advisory signing, agreement, AES and PQC generation choices; no login |
| `objects`, `inspect`, `certificate`, `export` | Persistent-object summaries, explicit attributes, certificate metadata and public export |
| `capabilities`, `plan`, `bind`, `sign` | Inspect a signing key, plan, prove certificate association or sign |
| `verify` | Software certificate verification or token verification with `--key` |
| `digest`, `mac`, `verify-mac` | Token digest and full-tag MAC operations |
| `aes-gcm-capabilities`, `encrypt-aes-gcm`, `decrypt-aes-gcm` | Authenticated encryption with explicit nonce/AAD |
| `encrypt-aes`, `decrypt-aes` | ECB/CBC/CBC-PAD; single-part or `--multipart` |
| `kem-capabilities`, `encapsulate`, `decapsulate` | ML-KEM capability checks and persistent shared secrets |
| `hkdf-capabilities`, `derive-hkdf`, `derive-hybrid`, `derive-kbkdf`, `derive-montgomery` | Token-held key derivation |
| `random` | Token-generated bytes |
| `diagnose` | Bounded pool capacity/exhaustion/reuse; not a benchmark or fault-injection test |
| `generate`, `import`, `set-label`, `delete` | Persistent-object creation, relabel or deletion; require `--confirm` |
| `init-token`, `init-pin`, `set-pin` | Token/PIN administration; require `--confirm` |

## Authentication and output

| Option or behavior | Contract |
| --- | --- |
| `--pin-file PATH` / `--protected-path` | Mutually exclusive; no plaintext PIN argument or implicit prompt |
| `--role user\|so` | USER by default; SO opens RW sessions, pooled signing uses USER/RO |
| PIN file | UTF-8, at most 65536 bytes; remove one final LF/CRLF only; `/dev/fd/3` paths accepted; read once |
| `--context-pin-file` / `--context-protected-path` | Separate always-authenticate signing credential |
| `--input -` | Read stdin where supported; secondary context/AAD/certificate files require paths |
| `--output PATH` | Exclusive creation, Unix mode 0600; existing files preserved; destination reserved before module loading |
| `--output -` | Raw binary stdout, including with JSON selected |
| Cleanup | Checked client/session close and provider finalization before output; incomplete new files removed on failure |

Protect PIN sources with operating-system access controls. Buffers are zeroizing,
borrowed by library calls and excluded from diagnostics. Login state is token-wide;
no authentication leaves it unchanged, and an existing role may not recheck a PIN.
Files/pipes and failed operations are never retried.

Bound signing performs two signatures, requiring context authentication for each.
Raw/prehashed always-authenticate signing is unsupported by the binding; protected
paths require token support. Token/PIN mutations require host PIN files.

Close/finalization errors use exit 5 and retain primary operation errors. An output
or cleanup failure does not undo a signature or mutation; an error can follow
persistent effects. There is no automatic rollback.

## Inspection and public export

`objects` requests no secret values. Its `uri` is null when metadata cannot form a
supported selector; duplicate locators can still fail later resolution.
`inspect --attributes` accepts these comma-separated names:

```text
class, label, id, object-id, private, sign, sensitive, extractable,
always-authenticate, key-type, modulus, exponent, ec-params, ec-point,
subject, issuer, serial, value
```

Defaults are class/label/ID. Explicit `value` can expose application data if the
token permits it. Status distinguishes available, unsupported, sensitive and
unavailable; bytes are hexadecimal, with an additional UTF-8 label field when valid.

`export` refuses private objects and private/secret-key classes. It writes raw
certificate/data CKA_VALUE or validated SPKI DER. `--key-family` selects classical,
ML-DSA, ML-KEM, SLH-DSA, EdDSA or Montgomery public-key handling as supported by the command;
`capabilities`, `certificate` and `bind` accept classical, ML-DSA and EdDSA.
Certificate import/raw export do not require a family option. Parsing/export never
establishes peer or certificate trust.

## Classical signing

```sh
pkcs11ctl --module /path/to/module.so sign \
  --key 'pkcs11:serial=123;id=%01;type=private' \
  --algorithm rsa-pkcs1 --digest sha256 --input message.bin \
  --output signature.bin --pin-file /secure/user.pin
```

| Option | Profile |
| --- | --- |
| `--algorithm` | `rsa-pkcs1`, `rsa-pss` or `ecdsa` |
| `--digest` | SHA-256/384/512; SHA-1 requires `--allow-sha1`, SHA-224 requires `--allow-sha224` |
| `--input-kind message\|digest` | Message by default; digest length must match and is never rehashed |
| `--hashing token\|allow-software\|software` | Token by default; explicit pre-operation plan selection, no retry after failure |
| PSS | Require `--mgf-digest` and `--salt-length`; bound PSS requires matching message/MGF digests |
| `--certificate URI` | Bind once, then verify each message signature; unsupported parameters fail before the probe |

Policy requires RSA of at least 2048 bits and supported curves/algorithms. Generic
PSS permits independent MGF parameters subject to provider acceptance. `plan`
performs no signature/binding and takes no certificate. `bind` uses the same hashing
choices. Labels/IDs do not prove association, and binding does not establish trust.

RSA signatures are modulus-width bytes; ECDSA is fixed-width `r || s`, not DER.
No DER/PEM conversion is supplied. SHA-1 DigestInfo uses OID `1.3.14.3.2.26`.

## ML-DSA, EdDSA and SLH-DSA

```sh
pkcs11ctl --module /path/to/module.so generate \
  --token 'pkcs11:serial=123' --kind ml-dsa-65 --id 01 --label signing \
  --pin-file /secure/user.pin --confirm
pkcs11ctl --module /path/to/module.so sign \
  --key 'pkcs11:serial=123;id=%01;type=private' \
  --algorithm ml-dsa-65 --input message.bin --context-file context.bin \
  --hedging required --output signature.bin --pin-file /secure/user.pin
pkcs11ctl verify --certificate-file certificate.der \
  --algorithm ml-dsa-65 --input message.bin --context-file context.bin \
  --signature signature.bin
```

Pure ML-DSA uses `--algorithm ml-dsa-44|ml-dsa-65|ml-dsa-87`, rejecting digest input,
`--digest`, PSS and `--hashing`. Messages are at most 64 MiB and may be empty;
`--context-file` supplies up to 255 binary bytes, empty by default, from a file.
Verification requires the same context.

`--hedging required|preferred|deterministic` applies to signing/planning, defaulting
to required. Required needs fresh token randomness; preferred allows either provider
mode; deterministic requires repeatable signing. `plan` reports current parameters
and context authentication without signing. Bound signing verifies in software;
the binding probe always uses required hedging, independent of message policy.
ML-DSA public export writes RFC 9881 SPKI DER.

```sh
pkcs11ctl generate --module /path/lib.so --token 'pkcs11:token=test' \
  --kind ed25519 --id 96 --label ed25519 --confirm
pkcs11ctl sign --module /path/lib.so \
  --key 'pkcs11:token=test;object=ed25519;type=private' \
  --algorithm ed25519 --input message.bin --output signature.bin --pin-file user.pin
pkcs11ctl export --module /path/lib.so \
  --object 'pkcs11:token=test;object=ed25519;type=public' \
  --key-family eddsa --output public.der --pin-file user.pin
```

Ed25519/Ed448 sign the original message with no external digest, context or hashing
policy. Context-authenticated EdDSA is unsupported.

```sh
pkcs11ctl generate --module /path/lib.so --token 'pkcs11:token=test' \
  --kind slh-dsa-sha2-128s --id 40 --label slh --confirm
pkcs11ctl sign --module /path/lib.so \
  --key 'pkcs11:token=test;object=slh;type=private' \
  --algorithm slh-dsa-sha2-128s --input message.bin --output signature.bin
```

Pure SLH-DSA generation uses `--kind slh-dsa-*`. HashSLH-DSA needs a separate
`--kind hash-slh-dsa-*` pair with disjoint allowed mechanisms. HashML-DSA and
HashSLH-DSA select `--algorithm hash-ml-dsa|hash-slh-dsa`, explicit `--parameter-set`
and `--digest`:

```sh
pkcs11ctl sign --module /path/lib.so \
  --key 'pkcs11:token=test;object=mldsa;type=private' \
  --algorithm hash-ml-dsa --parameter-set ml-dsa-65 --digest sha256 \
  --input message.bin --output signature.bin --pin-file user.pin
```

`--input-kind digest` supplies an exact-length SHA-2 digest. SHA-3/SHAKE are
available for token-hashed messages; the binding cannot represent their caller-
supplied digests. Generated HashSLH-only pairs exclude SHAKE mechanisms.
SLH-DSA/hash-PQC certificate verification is unsupported; use
`verify --key` for token verification.

## Verification and random bytes

```sh
pkcs11ctl verify --certificate-file certificate.der \
  --algorithm rsa-pkcs1 --digest sha256 --input message.bin \
  --signature signature.bin
pkcs11ctl --module /path/to/module.so random \
  --token 'pkcs11:serial=123' --length 32 --output random.bin
```

| Verification source | Execution |
| --- | --- |
| `--certificate-file PATH` | Software verification from X.509 DER; no module/login |
| `--certificate URI` | Software verification from a token certificate; optional USER login |
| `--key URI` with `type=public` | Token verification for classical, EdDSA, ML-DSA, SLH-DSA and hash-PQC |

Verification uses matching signing input parameters, without `--hashing`.
Certificate success reports `verified: true`, `trust_validated: false`; mismatch
uses exit 4. Issuer, validity, usage, revocation and trust chains are not checked.
Message/signature/certificate-file limits are 64 MiB/64 KiB/1 MiB. Either message or
signature can read stdin, but not both. Certificate files require a path.

`random` requests 1–1048576 bytes in one token call; authentication is optional,
subject to token policy. It adds no software fallback or seeding. Bytes remain
zeroizing until output completes or fails.

## AES-GCM files

```sh
# NONCE_HEX must be a nonce not previously used with this key.
pkcs11ctl --module /path/to/module.so encrypt-aes-gcm \
  --object 'pkcs11:serial=123;id=%31;type=secret-key' --nonce "$NONCE_HEX" \
  --aad-file context.bin --input message.bin --output ciphertext.bin --pin-file user.pin
pkcs11ctl --module /path/to/module.so decrypt-aes-gcm \
  --object 'pkcs11:serial=123;id=%31;type=secret-key' --nonce "$NONCE_HEX" \
  --aad-file context.bin --input ciphertext.bin --output recovered.bin --pin-file user.pin
```

Use an AES `type=secret-key` URI, a 12-byte nonce as exactly 24 hexadecimal digits,
input and output. Optional `--aad-file` needs a path; omit it for empty AAD.
The raw format is ciphertext followed by the full 16-byte tag, without nonce/AAD/
header. Retain nonce and AAD separately. Plaintext is at most 16 MiB, AAD 1 MiB;
empty input is valid and decryption requires at least the tag.

**Never reuse a nonce with the same key**, including across applications, restarts
or key copies. An encryption error does not permit reuse. No nonce generation,
tracking or envelope is provided. Generated encryption keys and HKDF AES outputs
qualify; wrapping-only keys do not. `aes-gcm-capabilities` checks advisory support.

Authentication and checked cleanup precede plaintext output. Inputs/plaintext
zeroize on drop; cryptoki failed-call temporary buffers cannot be guaranteed wiped.
Errors use stderr without plaintext.

## Digest, MAC, AES block modes and SP 800-108

```sh
pkcs11ctl mechanisms --module /path/lib.so --token 'pkcs11:token=test'
pkcs11ctl function-support --module /path/lib.so --token 'pkcs11:token=test'
pkcs11ctl digest --module /path/lib.so --token 'pkcs11:token=test' \
  --algorithm sha256 --input message.bin --output digest.bin
pkcs11ctl mac --module /path/lib.so \
  --object 'pkcs11:token=test;object=hmac;type=secret-key' \
  --algorithm hmac-sha256 --input message.bin --output tag.bin
pkcs11ctl verify-mac --module /path/lib.so \
  --object 'pkcs11:token=test;object=hmac;type=secret-key' \
  --algorithm hmac-sha256 --input message.bin --tag tag.bin
pkcs11ctl encrypt-aes --module /path/lib.so \
  --object 'pkcs11:token=test;object=aes;type=secret-key' \
  --mode cbc --iv 000102030405060708090a0b0c0d0e0f \
  --input plaintext.bin --output ciphertext.bin
pkcs11ctl decrypt-aes --module /path/lib.so \
  --object 'pkcs11:token=test;object=aes;type=secret-key' \
  --mode cbc --iv 000102030405060708090a0b0c0d0e0f \
  --input ciphertext.bin --output plaintext.bin
pkcs11ctl derive-kbkdf --module /path/lib.so \
  --object 'pkcs11:token=test;object=base;type=secret-key' \
  --prf hmac-sha256 --mode counter --kind aes256 \
  --kdf-label-file label.bin --kdf-context-file context.bin \
  --id 30 --label derived --confirm
```

`digest`, `mac`, `verify-mac`, `encrypt-aes` and `decrypt-aes` accept `--multipart`;
single-part is the default. Mechanism metadata distinguishes advertisement from
typed execution support; provider parameters remain authoritative. See the
[compatibility matrix](https://github.com/Juanbanpar/pkcs11-stack/blob/main/docs/oasis-compatibility.md) and command help for
algorithm, IV, padding and KDF options. ECB/CBC do not provide authentication.

## ML-KEM and HKDF

Generate `ml-kem-512|ml-kem-768|ml-kem-1024` pairs, then export/import RFC 9935
public SPKI with `--key-family ml-kem` / `import --kind ml-kem`. Private-key
import/export, `--bits` and always-authenticate ML-KEM generation are unavailable.

```sh
pkcs11ctl --module /path/to/module.so encapsulate \
  --object 'pkcs11:serial=123;id=%01;type=public' \
  --parameter-set ml-kem-768 --id 0200 --label sender-secret \
  --pin-file /secure/user.pin --output ciphertext.bin --confirm
pkcs11ctl --module /path/to/module.so decapsulate \
  --object 'pkcs11:serial=456;id=%01;type=private' \
  --parameter-set ml-kem-768 --id 0201 --label recipient-secret \
  --pin-file /secure/user.pin --input ciphertext.bin --confirm
pkcs11ctl --module /path/to/module.so derive-hkdf \
  --object 'pkcs11:serial=123;id=%02%00;type=secret-key' \
  --digest sha256 --kind aes256 --id 03 --label application-key \
  --salt-file public-salt.bin --info-file protocol-context.bin \
  --pin-file /secure/user.pin --confirm
```

Run commands against each peer's module/token. Encapsulation writes only public
ciphertext; decapsulation checks exact length before loading. Both create private,
sensitive, nonextractable 32-byte generic secrets with derivation permission only
and require new IDs. `kem-capabilities --operation encapsulate|decapsulate` checks
support without creation.

`hkdf-capabilities --digest sha256|sha384|sha512` checks a sensitive/nonextractable
generic/HKDF derivation base matching the hash length. `derive-hkdf` performs
extract-and-expand; ML-KEM secrets use SHA-256. `--kind aes128|aes192|aes256` creates
encryption keys; `derivation-secret --length N` permits only further derivation.
Salt/context files are public, up to 4096 bytes each, and cannot be stdin; omitted
salt means zero salt, omitted context is allowed. Outputs stay private, sensitive
and nonextractable.

`derive-hybrid --object CLASSICAL --post-quantum PQ --digest sha512` concatenates
P-256 ECDH then ML-KEM-768 secrets and applies HKDF-SHA512. Both inputs must be
distinct 32-byte sensitive/nonextractable generic secrets permitting derivation
and concatenation. Output/identity options follow HKDF; salt is at most 128 bytes
and `--info-file` must be nonempty. The temporary combined key is destroyed before
return; inputs remain until explicitly deleted.

Authenticate peers, establish independent component provenance and bind protocol
context. This combiner defines neither a hybrid wire protocol nor X-Wing/TLS.
ML-KEM implicit rejection can produce a different secret for altered same-length
ciphertext without error; success does not authenticate the sender. All creation
requires `--confirm` and RW mode; errors can leave objects needing explicit removal.

## Montgomery agreement

```sh
pkcs11ctl generate --module /path/lib.so --token 'pkcs11:token=test' \
  --kind x25519 --id 70 --label x25519 --confirm
pkcs11ctl derive-montgomery --module /path/lib.so \
  --object 'pkcs11:token=test;object=x25519;type=private' \
  --curve x25519 --peer peer.bin --kdf null --kind derivation-secret --length 32 \
  --id 71 --label derived --confirm --pin-file user.pin
```

X25519/X448 use `derive-montgomery` and `export --key-family montgomery`. `--peer`
accepts raw RFC 7748 bytes or RFC 8410 SPKI. Choose the KDF/output explicitly;
private and derived key values stay on the token.

## Administration

Every mutation requires `--confirm`. `init-token` can erase all objects and requires
an explicit slot plus `--expected-token URI`. Copy the selected entry's complete
URI from `tokens`: `token`, `manufacturer`, `model` and `serial`, including explicit
empty values. Other attributes/queries are rejected. The CLI compares the slot's
criteria, then the client rechecks the snapshot immediately before initialization,
including for uninitialized tokens. Identical replacements and swaps after the
check cannot be detected; arrange exclusive physical access. All consumers must
close first. Token labels are at most 32 UTF-8 bytes.

| Command | Required inputs |
| --- | --- |
| `init-token` | `--slot`, `--expected-token`, `--label`, `--so-pin-file` |
| `init-pin` | `--token`, `--role so`, `--pin-file`, `--new-pin-file` |
| `set-pin` | `--token`, current role/PIN, `--new-pin-file` |
| `generate` | `--token`, `--kind`, hexadecimal `--id`, `--label` |
| `import` | `--token`, `--kind`, `--id`, `--label`, `--input` |
| `set-label` / `delete` | Unique `--object`; new label for relabeling |

```sh
pkcs11ctl --module /path/to/module.so generation-options --token 'pkcs11:serial=123'
pkcs11ctl --module /path/to/module.so generate --token 'pkcs11:serial=123' \
  --kind ecdh-p256 --id 31 --label agreement --pin-file user.pin --confirm
pkcs11ctl --module /path/to/module.so generate --token 'pkcs11:serial=123' \
  --kind aes256 --purpose wrapping --id 32 --label wrapper --pin-file user.pin --confirm
```

| Generation family | Options and permissions |
| --- | --- |
| RSA | 2048 bits by default; `--bits` accepts multiples of 8 from 2048–16384 within provider bounds |
| P-256/P-384/P-521, EdDSA, ML-DSA, SLH-DSA/hash-SLH | Signing pairs; `--always-authenticate` only where supported |
| `ecdh-p256\|ecdh-p384\|ecdh-p521`, X25519/X448 | Agreement pairs |
| ML-KEM | Encapsulation/decapsulation pairs |
| AES | `--purpose encryption`, `wrapping` or `authentication` |
| HMAC | Persistent MAC keys such as `--kind hmac-sha256` |

```sh
pkcs11ctl generate --module /path/lib.so --token 'pkcs11:token=test' \
  --kind hmac-sha256 --id 50 --label hmac --confirm
pkcs11ctl generate --module /path/lib.so --token 'pkcs11:token=test' \
  --kind aes128 --purpose authentication --id 51 --label cmac --confirm
pkcs11ctl import --module /path/lib.so --token 'pkcs11:token=test' \
  --kind public-key --purpose verification --id 90 --label imported \
  --input public.der --confirm
```

Private/secret keys are sensitive/nonextractable and no values are returned.
Generation choices do not guarantee later use/template acceptance. ECDH/AES
IDs/labels require 1–128 bytes and reject existing pair/secret IDs respectively;
other generation can permit duplicates. Concurrent uniqueness is not guaranteed.
Invalid option combinations fail before loading.

Certificate import accepts exact X.509 DER, including algorithms outside signing
support, without validating trust. Data is uninterpreted. `--id` maps to CKA_ID for
keys/certificates and CKA_OBJECT_ID for data; select data by label. Imports create
persistent public objects. Raw certificate export/inspection are independent of
signing support. Private/secret-key import/export, arbitrary JSON templates,
RSA-OAEP, raw EC derivation and wrapping are not CLI commands; use library APIs
or the desktop where supported.

## Output and exit codes

JSON success has `schema_version: 1`, `command` and `result`; errors on stderr have
`schema_version: 1` and `error: {kind, message}`. Binary commands emit no success
JSON; format still controls errors. Parsing errors redact raw arguments. Text
records escape user-controlled fields, preventing terminal control injection.

| Exit | Meaning |
| --- | --- |
| 0 | Success or requested help/version |
| 2 | Arguments, URI constraints or input parameters |
| 3 | Missing or ambiguous selection |
| 4 | Policy, unsupported parsing/verification or signature/binding mismatch |
| 5 | Runtime/provider/loading/cleanup failure |
| 6 | File or output I/O failure |

Mechanism names and session states are diagnostic strings. Attribute status/value
fields follow the inspection contract; raw object handles are never exposed.
`diagnose` permits pool sizes 1–64.
