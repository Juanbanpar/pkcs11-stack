# pkcs11ctl

A command-line tool for inspecting, provisioning, and using PKCS#11 tokens.
Use it for one-off checks or automate token workflows with JSON output and
process exit codes.

## Installation

Use Rust 1.88 or newer with Cargo and a native linker. Use these commands
after version `0.1.0` is published on crates.io.

```sh
cargo install --locked pkcs11ctl --version 0.1.0
pkcs11ctl --help
```

To build from a local checkout, run the following from the repository root.

```sh
cargo build --release -p pkcs11ctl --locked
./target/release/pkcs11ctl --module /path/to/pkcs11.so --format json tokens
```

## Discover tokens

The examples below assume `pkcs11ctl` is on your PATH. From a checkout, use
`./target/release/pkcs11ctl` in its place. Use a trusted vendor module or follow
the [disposable SoftHSM quickstart](https://github.com/Juanbanpar/pkcs11-stack/blob/main/docs/quickstart.md)
to generate a key, sign, and verify.
Use the [troubleshooting guide](https://github.com/Juanbanpar/pkcs11-stack/blob/main/docs/troubleshooting.md)
for module, token, and authentication failures.

```sh
pkcs11ctl --module /path/to/pkcs11.so tokens
pkcs11ctl --module /path/to/pkcs11.so --format json info
pkcs11ctl sign --help
```

| Input | Rules |
| --- | --- |
| Module | Load trusted executable code explicitly with `--module`. It and `--format text\|json` can appear before or after the command. Help, version, and `verify --certificate-file` run without a module |
| Object URI | Copy a URI from `objects` when available or build one from a stable token serial and object ID. For example, `id=%01;type=private` selects a private key with binary ID `01`. Use `type=cert` for a certificate |
| Matching | Full token criteria are checked. Object selectors must match exactly once. Empty URI fields match empty attributes. Unsupported constraints, PIN queries, and persistent slot IDs fail before loading |
| Slot IDs | Use for discovery and initialization |

## Commands

Use `pkcs11ctl COMMAND --help` for complete options.

| Commands | Purpose |
| --- | --- |
| `info`, `slots`, `tokens` | Library, slot and token metadata, including stable token URIs |
| `mechanisms`, `function-support` | Advertised mechanisms, typed executable paths and interface functions |
| `generation-options` | Advisory signing, agreement, AES and PQC generation choices without login |
| `objects`, `inspect`, `certificate`, `export` | Persistent-object summaries, explicit attributes, certificate metadata and public export |
| `capabilities`, `plan`, `bind`, `sign` | Inspect a signing key, plan, prove certificate association or sign |
| `verify` | Software certificate verification or token verification with `--key` |
| `digest`, `mac`, `verify-mac` | Token digest and full-tag MAC operations |
| `aes-gcm-capabilities`, `encrypt-aes-gcm`, `decrypt-aes-gcm` | Authenticated encryption with explicit nonce/AAD |
| `aes-cipher-capabilities`, `encrypt-aes`, `decrypt-aes` | Inspect or use ECB, CBC, and CBC-PAD. Supports single-part or `--multipart` |
| `kem-capabilities`, `encapsulate`, `decapsulate` | ML-KEM capability checks and persistent shared secrets |
| `hkdf-capabilities`, `derive-hkdf`, `derive-hybrid`, `derive-kbkdf`, `derive-montgomery` | Token-held key derivation |
| `random` | Token-generated bytes |
| `diagnose` | Check bounded pool capacity, exhaustion, and lease reuse |
| `generate`, `import`, `set-label`, `delete` | Create, relabel, or delete persistent objects with `--confirm` |
| `init-token`, `init-pin`, `set-pin` | Administer tokens and PINs with `--confirm` |

## Authentication and output

| Option or behavior | Contract |
| --- | --- |
| `--pin-file PATH` / `--protected-path` | Mutually exclusive. No plaintext PIN argument or implicit prompt |
| `--role user\|so` | USER by default. SO opens RW sessions, pooled signing uses USER/RO |
| PIN file | UTF-8, at most 65536 bytes. Remove one final LF/CRLF only. `/dev/fd/3` paths accepted. Read once |
| `--context-pin-file` / `--context-protected-path` | Separate always-authenticate signing credential |
| `--input -` | Read stdin where supported. Secondary context/AAD/certificate files require paths |
| `--output PATH` | Exclusive creation, Unix mode 0600. Existing files preserved. Destination reserved before module loading |
| `--output -` | Raw binary stdout, including with JSON selected |
| Cleanup | Checked client/session close and provider finalization before output. Incomplete new files removed on failure |

- Restrict access to PIN files. PIN buffers zeroize and stay out of diagnostics.
- Login is token-wide. Omitted authentication leaves the role as is. An active
  role may proceed without a fresh PIN check.
- Bound signing performs a probe and a message signature. Always-authenticate
  keys need context credentials for both. Raw and prehashed profiles cannot use
  those credentials. Token and PIN administration requires host PIN files.
- Files, pipes, and failed operations are read or attempted once. Cleanup failures
  use exit 5 and retain the original operation error. A mutation can take effect
  before cleanup or file output fails. Inspect the token before trying again.

## Inspection and public export

`objects` requests no secret values. Its `uri` is null when metadata cannot form a
supported selector. Duplicate locators can still fail later resolution.
`inspect --attributes` accepts these comma-separated names:

```text
class, label, id, object-id, private, sign, sensitive, extractable,
always-authenticate, key-type, modulus, exponent, ec-params, ec-point,
subject, issuer, serial, value
```

Defaults are class/label/ID. Explicit `value` can expose application data if the
token permits it. Status distinguishes available, unsupported, sensitive and
unavailable. Attribute bytes are hexadecimal, with an additional UTF-8 label
field when valid.

`export` refuses private objects and private/secret-key classes. It writes raw
certificate/data CKA_VALUE or validated SPKI DER. `--key-family` selects classical,
ML-DSA, ML-KEM, SLH-DSA, EdDSA, or Montgomery public-key handling.
`capabilities`, `certificate`, and `bind` accept classical, ML-DSA, and EdDSA.
Certificate import and raw export work independently of the certificate's
signing algorithm. Check certificate trust separately.

## Classical signing

```sh
pkcs11ctl --module /path/to/module.so sign \
  --key 'pkcs11:serial=123;id=%01;type=private' \
  --algorithm rsa-pkcs1 --digest sha256 --input message.bin \
  --output signature.bin --pin-file /secure/user.pin
```

| Option | Profile |
| --- | --- |
| `--algorithm` | `rsa-pkcs1`, `rsa-pss` or `ecdsa` |
| `--digest` | SHA-256/384/512. SHA-1 requires `--allow-sha1`, SHA-224 requires `--allow-sha224` |
| `--input-kind message\|digest` | Message by default. Digest length must match and is never rehashed |
| `--hashing token\|allow-software\|software` | Token by default. Explicit pre-operation plan selection, no retry after failure |
| PSS | Require `--mgf-digest` and `--salt-length`. Bound PSS requires matching message/MGF digests |
| `--certificate URI` | Bind once, then verify each message signature. Unsupported parameters fail before the probe |

- RSA keys require at least 2048 bits. Unbound PSS permits independent MGF
  parameters if the provider accepts them. SHA-1 DigestInfo uses OID `1.3.14.3.2.26`.
- `plan` inspects the request before binding or signing and takes no certificate.
  `bind` uses the same hashing choices to prove that a key matches a certificate.
- RSA signatures are modulus-width bytes. ECDSA signatures use raw fixed-width
  `r || s`. Callers handle format conversion and certificate trust.

## ML-DSA, EdDSA and SLH-DSA

For the ML-DSA verification step, use a DER certificate issued for the
generated public key.

```sh
pkcs11ctl --module /path/to/module.so generate \
  --token 'pkcs11:serial=123' --kind ml-dsa-65 --id 01 --label signing \
  --pin-file /secure/user.pin --confirm
pkcs11ctl --module /path/to/module.so sign \
  --key 'pkcs11:serial=123;id=%01;type=private' \
  --algorithm ml-dsa-65 --input message.bin --context-file context.bin \
  --hedging required --output signature.bin --pin-file /secure/user.pin
pkcs11ctl verify --certificate-file certificate.der \
  --algorithm ml-dsa-65 --input message.bin --context-file context.bin \
  --signature signature.bin
```

| Pure ML-DSA option | Behavior |
| --- | --- |
| Algorithm and input | `ml-dsa-44`, `ml-dsa-65`, or `ml-dsa-87`. Original message, 0–64 MiB. Digest input, PSS, and hashing options are rejected |
| `--context-file` | Up to 255 binary bytes. Defaults to empty. Use the same context for verification |
| `--hedging` | `required` (default) needs fresh token randomness. `preferred` accepts either mode. `deterministic` requires repeatable signing |
| Planning and binding | `plan` reports parameters and context authentication before signing. The binding probe always requires hedging. Bound signatures are checked in software |
| Export | RFC 9881 SPKI DER |

```sh
pkcs11ctl generate --module /path/lib.so --token 'pkcs11:token=test' \
  --kind ed25519 --id 96 --label ed25519 --pin-file user.pin --confirm
pkcs11ctl sign --module /path/lib.so \
  --key 'pkcs11:token=test;object=ed25519;type=private' \
  --algorithm ed25519 --input message.bin --output signature.bin --pin-file user.pin
pkcs11ctl export --module /path/lib.so \
  --object 'pkcs11:token=test;object=ed25519;type=public' \
  --key-family eddsa --output public.der --pin-file user.pin
```

Ed25519/Ed448 sign the original message with no external digest, context or hashing
policy. Context-authenticated EdDSA is unsupported.

```sh
pkcs11ctl generate --module /path/lib.so --token 'pkcs11:token=test' \
  --kind slh-dsa-sha2-128s --id 40 --label slh --pin-file user.pin --confirm
pkcs11ctl sign --module /path/lib.so \
  --key 'pkcs11:token=test;object=slh;type=private' \
  --algorithm slh-dsa-sha2-128s --input message.bin --output signature.bin --pin-file user.pin
```

Pure SLH-DSA generation uses `--kind slh-dsa-*`. HashSLH-DSA needs a separate
`--kind hash-slh-dsa-*` pair with disjoint allowed mechanisms. HashML-DSA and
HashSLH-DSA select `--algorithm hash-ml-dsa|hash-slh-dsa`, explicit `--parameter-set`
and `--digest`:

```sh
pkcs11ctl sign --module /path/lib.so \
  --key 'pkcs11:token=test;object=mldsa;type=private' \
  --algorithm hash-ml-dsa --parameter-set ml-dsa-65 --digest sha256 \
  --input message.bin --output signature.bin --pin-file user.pin
```

`--input-kind digest` supplies an exact-length SHA-2 digest. SHA-3/SHAKE are
available for token-hashed messages. Generated HashSLH-only pairs exclude
SHAKE mechanisms. Use `verify --key` for SLH-DSA and hash-PQC verification.

## Verification and random bytes

```sh
pkcs11ctl verify --certificate-file certificate.der \
  --algorithm rsa-pkcs1 --digest sha256 --input message.bin \
  --signature signature.bin
pkcs11ctl --module /path/to/module.so random \
  --token 'pkcs11:serial=123' --length 32 --output random.bin
```

| Verification source | Execution |
| --- | --- |
| `--certificate-file PATH` | Software verification from X.509 DER. No module/login |
| `--certificate URI` | Software verification from a token certificate. Optional USER login |
| `--key URI` with `type=public` | Token verification for classical, EdDSA, ML-DSA, SLH-DSA and hash-PQC |

- Match the signing input parameters and omit `--hashing`. Certificate success
  reports `verified: true` and `trust_validated: false`. A mismatch exits with
  code 4. Check issuer, validity, usage, revocation, and chain trust separately.
- Limits are 64 MiB for the message, 64 KiB for the signature, and 1 MiB for the
  certificate. At most one input can use stdin. Certificate files require a path.
- `random` requests 1–1048576 bytes from the token in one call with no software
  fallback or seeding. Authenticate if required. The output buffer zeroizes after use.

## AES-GCM files

This example uses an existing AES encryption key with the one-byte ID `31`.

```sh
# NONCE_HEX must be a nonce not previously used with this key.
pkcs11ctl --module /path/to/module.so encrypt-aes-gcm \
  --object 'pkcs11:serial=123;id=%31;type=secret-key' --nonce "$NONCE_HEX" \
  --aad-file context.bin --input message.bin --output ciphertext.bin --pin-file user.pin
pkcs11ctl --module /path/to/module.so decrypt-aes-gcm \
  --object 'pkcs11:serial=123;id=%31;type=secret-key' --nonce "$NONCE_HEX" \
  --aad-file context.bin --input ciphertext.bin --output recovered.bin --pin-file user.pin
```

| Area | Contract |
| --- | --- |
| Key | Encryption-enabled AES secret key, including generated encryption keys and HKDF AES outputs. Use `aes-gcm-capabilities` to check direction support |
| Nonce | 12 bytes as 24 hex digits. **Never reuse a nonce with the same key**, including across applications, restarts, key copies, or after an encryption error. Callers generate and track nonces |
| AAD and limits | Optional file, up to 1 MiB. Omit for empty AAD. Plaintext can be 0–16 MiB |
| Binary format | Ciphertext followed by a 16-byte tag. Store the nonce and AAD separately. Decryption requires at least the tag |
| Decryption | Authenticates and checks cleanup before writing plaintext. Buffers zeroize on drop. Failed cryptoki calls can leave temporary buffers unwiped |

## Digest, MAC, AES block modes and SP 800-108

```sh
pkcs11ctl mechanisms --module /path/lib.so --token 'pkcs11:token=test'
pkcs11ctl function-support --module /path/lib.so --token 'pkcs11:token=test'
pkcs11ctl digest --module /path/lib.so --token 'pkcs11:token=test' \
  --algorithm sha256 --input message.bin --output digest.bin
pkcs11ctl mac --module /path/lib.so \
  --object 'pkcs11:token=test;object=hmac;type=secret-key' \
  --algorithm hmac-sha256 --input message.bin --output tag.bin --pin-file user.pin
pkcs11ctl verify-mac --module /path/lib.so \
  --object 'pkcs11:token=test;object=hmac;type=secret-key' \
  --algorithm hmac-sha256 --input message.bin --tag tag.bin --pin-file user.pin
# Supply a fresh, unpredictable 16-byte CBC IV as 32 hex digits.
pkcs11ctl encrypt-aes --module /path/lib.so \
  --object 'pkcs11:token=test;object=aes;type=secret-key' \
  --mode cbc-pad --iv "$CBC_IV_HEX" \
  --input plaintext.bin --output cbc-ciphertext.bin --pin-file user.pin
pkcs11ctl decrypt-aes --module /path/lib.so \
  --object 'pkcs11:token=test;object=aes;type=secret-key' \
  --mode cbc-pad --iv "$CBC_IV_HEX" \
  --input cbc-ciphertext.bin --output cbc-recovered.bin --pin-file user.pin
pkcs11ctl derive-kbkdf --module /path/lib.so \
  --object 'pkcs11:token=test;object=base;type=secret-key' \
  --prf hmac-sha256 --mode counter --kind aes256 \
  --kdf-label-file label.bin --kdf-context-file context.bin \
  --id 30 --label derived --pin-file user.pin --confirm
```

`digest`, `mac`, `verify-mac`, `encrypt-aes`, and `decrypt-aes` default to
single-part operations and accept `--multipart`. Use AES-GCM when you need
authenticated encryption. See the
[compatibility matrix](https://github.com/Juanbanpar/pkcs11-stack/blob/main/docs/oasis-compatibility.md)
and command help for algorithm, IV, padding, and KDF options.

## ML-KEM and HKDF

Generate `ml-kem-512|ml-kem-768|ml-kem-1024` pairs, then export/import RFC 9935
public SPKI with `--key-family ml-kem` / `import --kind ml-kem`. Private-key
import/export, `--bits` and always-authenticate ML-KEM generation are unavailable.

```sh
pkcs11ctl --module /path/to/module.so encapsulate \
  --object 'pkcs11:serial=123;id=%01;type=public' \
  --parameter-set ml-kem-768 --id 0200 --label sender-secret \
  --pin-file /secure/user.pin --output ciphertext.bin --confirm
pkcs11ctl --module /path/to/module.so decapsulate \
  --object 'pkcs11:serial=456;id=%01;type=private' \
  --parameter-set ml-kem-768 --id 0201 --label recipient-secret \
  --pin-file /secure/user.pin --input ciphertext.bin --confirm
pkcs11ctl --module /path/to/module.so derive-hkdf \
  --object 'pkcs11:serial=123;id=%02%00;type=secret-key' \
  --digest sha256 --kind aes256 --id 03 --label application-key \
  --salt-file public-salt.bin --info-file protocol-context.bin \
  --pin-file /secure/user.pin --confirm
```

| Operation | Inputs and output |
| --- | --- |
| ML-KEM | Run commands against each peer's token. Encapsulation writes public ciphertext. Decapsulation checks exact length before loading. Both create private, sensitive, nonextractable 32-byte derivation secrets and require new IDs. `kem-capabilities --operation encapsulate\|decapsulate` checks support |
| HKDF base | `hkdf-capabilities --digest sha256\|sha384\|sha512` checks a sensitive, nonextractable generic/HKDF key matching the digest length. `derive-hkdf` performs extract-and-expand. Use SHA-256 for ML-KEM secrets |
| HKDF output | `--kind aes128\|aes192\|aes256` creates an encryption key. `--kind derivation-secret --length N` allows further derivation. Outputs are private, sensitive, and nonextractable |
| HKDF salt and context | Optional public files, up to 4096 bytes each. Omitted salt means zero salt. Stdin is reserved for primary input |
| Hybrid derivation | `derive-hybrid --object CLASSICAL --post-quantum PQ --digest sha512` concatenates P-256 ECDH then ML-KEM-768. Use two distinct 32-byte sensitive, nonextractable generic keys that permit derivation and concatenation. Output and identity options follow HKDF |
| Hybrid salt, context, and cleanup | At most 128 bytes of salt and a nonempty `--info-file`. The temporary combined key is destroyed and the component inputs remain |

- Authenticate peers, establish independent component provenance, and bind the
  protocol context. The combiner is an application primitive. X-Wing, wire
  protocols, and TLS use their own constructions.
- ML-KEM implicit rejection can produce a different secret for altered same-length
  ciphertext without reporting failure.
- New keys require `--confirm` and write access. Errors can leave objects that
  need explicit removal.

## Montgomery agreement

```sh
pkcs11ctl generate --module /path/lib.so --token 'pkcs11:token=test' \
  --kind x25519 --id 70 --label x25519 --pin-file user.pin --confirm
pkcs11ctl derive-montgomery --module /path/lib.so \
  --object 'pkcs11:token=test;object=x25519;type=private' \
  --curve x25519 --peer peer.bin --kdf null --kind derivation-secret --length 32 \
  --id 71 --label derived --confirm --pin-file user.pin
```

X25519/X448 use `derive-montgomery` and `export --key-family montgomery`. `--peer`
accepts raw RFC 7748 bytes or RFC 8410 SPKI. Choose the KDF and output explicitly.
Private and derived key values stay on the token.

## Administration

- Every mutation requires `--confirm`. `init-token` can erase all objects.
- Supply the slot and copy the complete `--expected-token` URI from `tokens`.
  Include `token`, `manufacturer`, `model`, and `serial` even when a field is
  empty. The CLI accepts exactly these attributes.
- The CLI checks slot criteria and the client rechecks the snapshot immediately
  before initialization, including for uninitialized tokens. Close other
  consumers and keep exclusive physical access to prevent a token swap.
- Token labels can contain up to 32 UTF-8 bytes.

| Command | Required inputs |
| --- | --- |
| `init-token` | `--slot`, `--expected-token`, `--label`, `--so-pin-file` |
| `init-pin` | `--token`, `--role so`, `--pin-file`, `--new-pin-file` |
| `set-pin` | `--token`, current role/PIN, `--new-pin-file` |
| `generate` | `--token`, `--kind`, hexadecimal `--id`, `--label` |
| `import` | `--token`, `--kind`, `--id`, `--label`, `--input` |
| `set-label` / `delete` | Unique `--object`. New label for relabeling |

```sh
pkcs11ctl --module /path/to/module.so generation-options --token 'pkcs11:serial=123'
pkcs11ctl --module /path/to/module.so generate --token 'pkcs11:serial=123' \
  --kind ecdh-p256 --id 31 --label agreement --pin-file user.pin --confirm
pkcs11ctl --module /path/to/module.so generate --token 'pkcs11:serial=123' \
  --kind aes256 --purpose wrapping --id 32 --label wrapper --pin-file user.pin --confirm
```

| Generation family | Options and permissions |
| --- | --- |
| RSA | 2048 bits by default. `--bits` accepts multiples of 8 from 2048–16384 within provider bounds |
| P-256/P-384/P-521, EdDSA, ML-DSA, SLH-DSA/hash-SLH | Signing pairs. `--always-authenticate` only where supported |
| `ecdh-p256\|ecdh-p384\|ecdh-p521`, X25519/X448 | Agreement pairs |
| ML-KEM | Encapsulation/decapsulation pairs |
| AES | `--purpose encryption`, `wrapping` or `authentication` |
| HMAC | Persistent MAC keys such as `--kind hmac-sha256` |

```sh
pkcs11ctl generate --module /path/lib.so --token 'pkcs11:token=test' \
  --kind hmac-sha256 --id 50 --label hmac --pin-file user.pin --confirm
pkcs11ctl generate --module /path/lib.so --token 'pkcs11:token=test' \
  --kind aes128 --purpose authentication --id 51 --label cmac --pin-file user.pin --confirm
pkcs11ctl import --module /path/lib.so --token 'pkcs11:token=test' \
  --kind public-key --purpose verification --id 90 --label imported \
  --input public.der --pin-file user.pin --confirm
```

| Area | Contract |
| --- | --- |
| Generated keys | Private and secret keys are sensitive and nonextractable. Generation choices are advisory. The provider checks templates and later use |
| IDs | ECDH and AES IDs and labels require 1–128 bytes. ECDH checks for existing pair IDs and AES checks for existing secret IDs. Other keys can share IDs. Concurrent writers can race duplicate checks. Invalid option combinations fail before loading |
| Import | Creates persistent public objects. X.509 certificates use exact DER and may carry algorithms outside signing support. Raw data is stored as supplied. Callers validate certificate trust |
| Locators | `--id` maps to CKA_ID for keys and certificates and CKA_OBJECT_ID for data. Select data objects by label |
| Other interfaces | The desktop and client library expose RSA-OAEP, raw EC derivation, and AES key wrapping. The CLI accepts its listed import formats and templates for public objects |

## Output and exit codes

JSON records have `schema_version: 1`. Structured success records contain
`command` and `result` on stdout. Errors contain `error.kind` and
`error.message` on stderr. For binary commands, use the exit status to check
success. Argument errors redact raw arguments and text output escapes
terminal control characters.

| Exit | Meaning |
| --- | --- |
| 0 | Success or requested help/version |
| 2 | Arguments, URI constraints or input parameters |
| 3 | Missing or ambiguous selection |
| 4 | Policy, unsupported parsing/verification or signature/binding mismatch |
| 5 | Runtime/provider/loading/cleanup failure |
| 6 | File or output I/O failure |

Mechanism names and session states are diagnostic strings. Attribute status/value
fields follow the inspection contract. Use URIs to select objects.
`diagnose` permits pool sizes 1–64.
